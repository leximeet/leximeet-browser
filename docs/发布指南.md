# 1.0.0发布指南

本指南用于从固定源码生成、验证和分发首版。实际发布结果以对应 tag、Release 和商店页面为准；本地构建不表示已经发布。[验收门禁](验收基线.md)

本仓首版正式标签为 `1.0.0`，与应用和安装包版本一致，不加 `v` 前缀。标签须指向最终验收提交；`SOURCE.json` 的提交和标签、对应源码归档及生产包须来自同一候选。上游 Dictionary 标签、依赖版本和第三方 Action 注释保持各自命名。

## 1. 构建与验证

```sh
npm ci
npm run format:check
npm run docs:check
npm run verify:connector
npm run typecheck
npm test
npm audit --omit=dev
npm run zip
npm run verify:manifest
npm run test:browser
npm run test:connected
```

`.output/chrome-mv3/` 是解压扩展，ZIP 位于 `.output/`。包内只提供 Dictionary 0.0.3 Lite Text；Core 是按需增量，Full 仅由 Desktop 使用。不得混入个人库、profile、原始报告、测试 fixture、本机 Native 注册或私人提交材料。

WXT 的 `zip` 会重新构建，应先生成 ZIP，再对同一生产字节运行 UI 与真实连接。归档时直接复制已验收的包，核对 ZIP CRC、每个文件的 SHA 和生产集合摘要；若重新构建或改变生产字节，须重新验收。

生产目录递归检查只允许根目录的 `manifest.json`；词典数据清单为 `dictionaries/core/dictionary-manifest.json`。旧词包生成目录由准备脚本整体替换，避免旧清单残留。

构建检查包括：manifest 版本 1.0.0、最低 Chromium 142、七项 API 权限和 HTTP/HTTPS 网站权限、冻结合同与声明一致、公开词包大小与摘要一致，以及完整许可。协议版本、来源和摘要从 `lib/connector/contracts/` 读取，不在维护指南中硬编码某次候选值。

## 2. 完整发行物

每次准备发行使用新的目录，依据配套来源清单选择物料，不混用不同构建的源码、扩展和测试报告。

```text
.output/release-1.0.0/<UTCtime>/
├── leximeet-browser-1.0.0-chrome.zip
├── leximeet-browser-source-1.0.0.tar.gz
├── LICENSE
├── SOURCE.json
└── SHA256SUMS
```

固定最终提交后，使用完整 `git archive --format=tar.gz --prefix=leximeet-browser/ <commit>` 生成对应源码，包含代码、测试、构建脚本、依赖锁、文档和许可，不含 Git 历史、缓存和个人资料。不能只打包部分业务目录或拼装未提交工作区。扩展 ZIP、根 LICENSE 和完整对应源码共同分发。[第三方与许可](第三方与许可.md)

`SOURCE.json` 记录源码提交、协议快照来源、词包锁、生产集合摘要、Browser/Desktop/Core 验收组合及实际结果和未验范围。`SHA256SUMS` 校验扩展、源码、LICENSE 和 SOURCE，不包含自身。下载后再次核对大小与 SHA。

## 3. 发布检查

- [ ] 固定源码和运行字节，工作区变更归属已确认。
- [ ] 公开文件、Git 历史、依赖和数据许可已检查；私人操作资料位于仓外。
- [ ] 基础、独立 UI 和真实连接门禁通过，人工验收及目标平台边界明确。
- [ ] 扩展、对应源码、许可、来源和校验文件齐备。
- [ ] 在宣布支持的正式浏览器检查扩展 ID、网站权限和 Native 安装、撤销与连接。
- [ ] 需要远端 CI 证据时运行对应工作流，记录 run URL 和源码提交。
- [ ] 经维护者确认后创建 tag、推送和发布；核对公开下载资产。

首版不迁移 0.x/rc 测试库。首次发布没有前一正式包；之后的版本升级按[兼容政策](版本与兼容.md)保留已有资料。源码链通过不替代实际桌面发行包验证；一个操作系统的结果不外推其他平台。

## 4. GitHub 与 Gitee

[GitHub](https://github.com/leximeet/leximeet-browser) 和 [Gitee](https://gitee.com/leximeet/leximeet-browser) 是平级的源码与协作入口。两平台的同一版本使用相同源码提交、同一个本地注解标签以及同一批 ZIP、源码、许可与校验文件；不要为第二个平台重新构建，也不要分别创建同名标签。上传后分别下载核对 SHA-256，某平台尚未发布时应明确标注。

最终验收通过后才创建 `1.0.0` 标签；在标签未公开前可以继续修改候选，不能把 package.json 版本号当作发布证据。标签一经公开便不移动，后续修复使用新版本。推送前检查两端 main，审阅并整合平台间的新贡献；只推送本轮 main 和版本标签，不推送本地开发历史，不使用 `--all`、`--mirror` 或强制覆盖。

当前 `.github/workflows` 在 GitHub Actions 执行，不会因 Gitee 有同名仓库而自动运行。固定提交上的本地测试、GitHub run、正式浏览器商店审核和两平台 Release 下载分别核验。词典下载仍采用锁文件中的 GitHub Dictionary Release；Gitee 源码托管不改变实际联网范围。

推送、创建 Release 和商店提交均由维护者明确授权。Chrome / Edge 商店的扩展 ID 与签名身份按商店实际分配，不由 Git 托管平台决定。

## 5. 浏览器商店

首次提交通过 Chrome Web Store 或 Edge Add-ons 后台上传扩展 ZIP，上传包内只允许根目录的一份 `manifest.json`。公开隐私政策、准确的功能与权限说明、图标和合规截图应与实际版本一致。[隐私政策](隐私政策.md) · [隐私与权限](隐私与权限.md)

具体后台填写表、账号配置、凭据和本次宣传物料放在仓外发布资料目录，不作为产品源码文档。商店审核结果、正式扩展 ID 及安装来源确认后，再更新公开安装入口。
