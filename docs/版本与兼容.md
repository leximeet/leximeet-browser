# 版本与兼容

## 首次发布

正式应用 1.0.0 前，不迁移 0.x/rc 测试库，不换算旧分数，也不保留旧手动掌握或旧 FSRS 解释器。测试使用新的隔离库；遇到未知格式时拒绝打开并保留原库，不自动清空真实用户资料。

当前个人资料格式为 `leximeet-browser-personal/4`，IndexedDB 结构版本为 4，只含六个正式 store。预发布 1/2/3 格式不双读、不转换；打开时会中止升级事务并保留原库。使用隔离 lab 生成新测试库，勿把格式不同的旧候选当作升级基线。

当前格式的事务、关闭重开、候选包替换、公共词包安装取消/恢复、连接封存和明确断开必须可靠。正式1.0.0之后，升级须保留已有事实和稳定ID；有模型变更才设计显式迁移、回滚与对应真实升级测试，不能用格式化或重建词典顺带重建个人库。

## 三种版本分开

| 版本                      | 用途                                              |
| ------------------------- | ------------------------------------------------- |
| Browser应用               | 功能与安装包，如1.0.0                             |
| LMCP合同/API              | 本地连接严格参数、响应与安全边界，快照摘要核验    |
| Dictionary发布/词条schema | 公共资产与词卡结构，如0.0.3 / `leximeet.entry.v2` |

本仓正式 Git 标签使用应用版本原文，首版为 `1.0.0`，不加 `v` 前缀。该约定不改变 LMCP 的业务版本协商，也不改写 Dictionary 或第三方依赖的版本命名。

`entry_id`用于公共词条身份，拼写用于搜索，分片文件/行号不是身份。独立Browser当前仍受normalized唯一索引约束；云端2.0接入前须重建统一实体身份和事件模型，而不是把Java/SQLite表直接搬进IndexedDB。

## 向后承诺

正式应用资料保留与协议版本兼容分别测试，构建身份与运行协商也分开：

- 构建：冻结本端合同、来源和每份文件的精确摘要；变更字节要重新验证，不能抄取对端摘要冒充。
- 正式1.x连接：API major相同、服务版本满足本端最低版本，且必需能力和方法齐全即可。不同合同摘要、较高minor/patch或新增可选响应字段不单独拒绝连接。
- 预发布：任一端是rc候选时，合同版本和摘要必须完全相同；不提供旧候选双栈。
- 原生通道：hello信封与结果版本一致，之后每帧保持协商版本；connectionId、requestId、方法、严格Schema及授权不放宽。

词包缺少字段时如实表示，不凭同名词猜测。共享规则和 FSRS 向量的稳定性不能替代序列化、授权或云合并验收。
